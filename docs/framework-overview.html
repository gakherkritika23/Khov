1 · What We Built

We built a production-grade end-to-end automation framework for the K. Hovnanian website (khov.com) using Playwright and TypeScript. The framework validates every customer-facing contact form across four distinct surfaces — the Contact Us page, QMI detail pages, floorplan detail pages, and community detail pages. Tests run headed (visible browser) against dev, UAT, stage, or production environments with a single command, and results are published live to a ReportPortal dashboard.

The framework is designed to be safe on production: forms are fully filled and validated, but submission is intentionally skipped on prod so no real leads are created. All API-level assertions run only on non-prod environments where there is no risk.

3 · Architecture Layers

The framework is structured in four clean layers. Each layer has a single responsibility.

npm script → Entry point. Sets TEST_ENV, invokes Playwright CLI, passes project/file filters.
playwright.config.ts → Loads environment/{env}.env → sets baseURL. Configures reporters, projects (Chrome / smoke / regression), slowMo, retries.
tests/baseTest.ts → Extends Playwright's base test with an afterEach hook that attaches a failure screenshot. All spec files import from here.
tests/*.spec.ts → Test specs. Orchestrate the flow: beforeEach navigation → test body actions → Validator assertions.
page-objects/ → Page Object Model classes. Each page gets one class. Locators defined as readonly Locator fields; actions are named methods.
page-objects/basePage.ts → Parent class. Shared primitives: click(), type(), navigate(), waitForVisible(), popup dismissal, retry navigation.
utils/ → Validator (named assertions), apiUtils (network intercept), testDataUtils (random names/emails), constants.json (URLs, text).
Browser (Chromium) → Headed, maximised window. slowMo 200 ms so every action is visible during the demo.

4 · Running the Demo — Step-by-Step

The command

npm run smoke:dev -- tests/contactForms.spec.ts

What happens, step by step

  1. 1

    npm run smoke:dev expands to cross-env TEST_ENV=dev npx playwright test --project=smoke. cross-env injects TEST_ENV=dev into the process environment before Playwright starts — this works identically on macOS, Linux, and Windows.

  2. 2

    playwright.config.ts loads the environment file. It reads TEST_ENV, picks the file environment/dev.env, and calls dotenv.config(). That file sets BASE_URL=https://www-dev.khov.com (and similar vars). The config then sets use.baseURL to that value. If BASE_URL is missing the config throws immediately — fail-fast.

  3. 3

    The smoke project is selected by --project=smoke. In the config this project has grep: /@smoke/, so Playwright only collects tests whose description string contains the @smoke tag.

  4. 4

    -- tests/contactForms.spec.ts (the part after --) is passed through as an extra Playwright argument that scopes execution to that single file.

  5. 5

    Playwright launches Chromium headed, maximised, with slowMo: 200 so every interaction is visible. One worker runs tests serially (no parallel browsers) to avoid contention on the live site.

  6. 6

    For each test: beforeEach instantiates the page object and navigates to the target URL. The test body calls action methods on the page object, which call BasePage primitives. Assertions go through Validator which wraps each in a named test.step() so reports show human-readable step names.

  7. 7

    afterEach (in baseTest.ts) runs after every test. If the test failed it captures a screenshot via page.screenshot() and attaches it to the test result. ReportPortal and the HTML report both display this attachment.

  8. 8

    Results are published to the ReportPortal dashboard (if RP_API_KEY is set in the env file) and saved to playwright-report/ (HTML).

5 · Test Lifecycle

// 1. Spec imports
import { test } from "./baseTest";        // always baseTest, never @playwright/test
import { expect } from "@playwright/test";  // expect imported separately
import { ContactUsPage } from "../page-objects/contactUsPage";

// 2. Describe block groups related tests
test.describe("Contact Us — Field & Dropdown Audit", () => {
  let contactUsPage: ContactUsPage;

  // 3. beforeEach: fresh navigation before every test
  test.beforeEach(async ({ page }) => {
    contactUsPage = new ContactUsPage(page);
    await contactUsPage.navigateToContactViaFooter(constants.home_page.url);
  });

  // 4. Each test: actions → Validator assertions
  test("TC-01 | Shopping for a new home @smoke", async () => {
    await contactUsPage.selectInterest("I am shopping for a new home");
    await contactUsPage.verifyFieldsForInterest("I am shopping for a new home");
    await contactUsPage.verifyRequiredFieldValidation(...);
    const resp = await contactUsPage.submitForm(...);  // null on prod
    if (resp) await contactUsPage.verifySubmissionSuccess(...);
  });

  // 5. afterEach (in baseTest.ts): screenshot on failure
  // test.afterEach → page.screenshot() → testInfo.attach("failure-screenshot")
});

6 · Page Object Model

Every page gets its own class that extends BasePage. Locators are declared as readonly Locator fields in the constructor (never hardcoded inline in tests). Methods describe user actions — selectInterest(), submitForm() — so tests read like a specification, not low-level Playwright calls. 

// page-objects/contactUsPage.ts (simplified)
export class ContactUsPage extends BasePage {
  private readonly interestRadio: Locator;
  private readonly firstNameInput: Locator;
  private readonly submitButton: Locator;

  constructor(page: Page) {
    super(page);
    this.interestRadio = page.locator('input[name="interest"]');
    this.firstNameInput = page.getByLabel("First Name");
    this.submitButton   = page.getByRole("button", { name: "Submit" });
  }

  async selectInterest(interest: ContactInterest): Promise<void> { /* ... */ }
  async verifyFieldsForInterest(interest: ContactInterest): Promise<void> { /* ... */ }
  async submitForm(interest: ContactInterest, endpoint: string): Promise<Response | null> { /* ... */ }
}

Shared form component

The Request Information modal (used on QMI, floorplan, and community pages) is extracted into its own class RequestInformationForm, which is composed into each page object as this.requestInfo. This avoids duplicating the modal verification and submission logic across multiple page objects.

8 · Production Safety

No real leads are ever created on production. Every form is fully filled and all field validations are exercised on every environment — but the actual HTTP submit call is skipped on prod. The submitForm() / submit() method returns null on prod and the test skips the success assertion branch.

On dev and UAT, submission goes through. The framework intercepts the /api/contact-us/ response via waitForApi(), asserts HTTP 200, and inspects the JSON payload to confirm the form data was correctly posted. 

// Non-prod: submit and assert API response
const response = await qmiPage.requestInfo.submit(constants.qmi.contact_us_api);
if (response) {
  await qmiPage.requestInfo.verifyApiSubmission(response);  // asserts HTTP 200 + payload
  await qmiPage.requestInfo.verifySubmissionSuccess();        // asserts success message on page
}
// On prod, response is null → if-block is skipped → no lead created
